## Data pipeline (src/, SQLite file `krungu.db`; db, logs and `out/` are gitignored)

Scripts are run in this order; each is resumable and rate-limited (Deezer 150ms, Last.fm 250ms, MusicBrainz 1.1s):

1. `bun run seed [maxArtists]`: Deezer charts (Indonesia playlist 1116188761 + global) expanded via top tracks / related artists. The "Top Indonesia" chart is mostly international, so it is not enough for local coverage.
2. `bun run seed:id`: curated Indonesian artists from `data/id-artists.txt` (edit the list, rerun). Sets `artists.local_seed = 1`.
3. `bun run country`: MusicBrainz lookup filling `country` + `mbid`. For local seeds only an ID-country namesake is accepted (the top name match is often a foreign namesake).
4. `bun run tags` (needs `LASTFM_API_KEY` in `.env`): Last.fm `artist.getTopTags` into `artist_tags`. Local artists without a verified mbid are skipped, and local artists whose top tags contain a foreign nationality are dropped (Last.fm merges some namesakes even by mbid, e.g. Tulus).
   Local artists without a verified mbid are looked up by name, but only trusted if their top tags contain an Indonesian marker.
4b. `bun run seed:related [maxNew]`: grows the catalog with Deezer related artists of every local artist (run before `country` and `tags`, which then pick up the new rows).
4c. Growth (added): `bun run seed:intl` (Deezer genre charts + `data/intl-artists.txt`, source `intl`), `bun run refresh [--full]` (album scan per local artist for new releases / full discography, plus Indonesian playlist discovery from `data/id-playlists.txt`; sets `tracks.year` from album date), `bun run explore [parents] [localShare]` (expands related artists of the least recently explored artists, local/intl 50/50), `bun run daily` (refresh + explore + country + tags + years + clean + moods, logs to `logs/`; schedule with Task Scheduler, see the header of `src/daily.ts`). New artists need `tags` before the engine sees them.
5. `bun run clean`: sets `tracks.playable` (non-destructive). Hides instrumental/karaoke/live/remix/slowed/cover/demo and tracks under 60s, and dedupes same artist + normalized title (strips remaster/version/edit notes), keeping the most popular copy. `loadCatalog()` only loads `playable = 1`; rerun after any new seeding.
5b. `bun run years` (Deezer `/track/:id`, ~11 min for 4.3k tracks): fills `tracks.year` (+ `isrc`). Resumable; rerun after new seeding. `release_date` is the seeded album's date, so reissues/compilations can be too late (track-level era is noisy).
5c. `bun run audio [events|all]`: Deezer `bpm`/`gain` per track into `tracks.bpm/gain` (0 = none). NOT used by the engine: Deezer has bpm for only ~50% of the tracks served to the owner (Indonesian and foreign alike), and on the owner's real log (65 plays, 21 finished) tempo did not predict finishes (AUC 0.49-0.51). Last.fm `track.getTopTags` was also probed: only 6/45 served tracks had tags (famous Western songs), so song-level tags are not a usable source for Indonesian music.
6. `bun run moods`: pure local recompute of `artist_moods` from tags (keyword table in `src/moods.ts`, 6 moods, absolute 0-1 scores). Retune the table and rerun; no API calls.

Notes: mood is artist-level only (tracks inherit it). `tracks.isrc` is not filled yet. Prefer `local_seed` over `country` to identify Indonesian artists; MusicBrainz coverage of local artists is thin.

## Radio engine (src/radio.ts) and simulator (src/sim.ts)

- `loadCatalog()` builds per-track feature vectors (L2-normalized `tag:*` + 0.7-scaled `mood:*` from the artist's tags, plus `era:*` from `tracks.year`: soft one-hot over 5-year buckets, own 1 / neighbours 0.4, scaled by `ERA_W` 0.6 after normalization); untagged artists are excluded, so the playable catalog is smaller than the DB. `pop:fam` = familiarity of the song (half within-artist popularity percentile from Deezer `rank`, half global log-rank), scaled by `FAM_W` 0.6: without it every track of an artist looked identical to the model, so known artists played random deep cuts (owner feedback, confirmed: served avg familiarity equalled the catalog's). `Profile.prior` starts with `pop:fam = 1` (popularity prior, the listener's own plays override it). `tracks.year` used for era is the earliest year among same-artist same-title copies. The LinUCB vocabulary is the top 100 tags + moods + eras + `pop:fam` (`VOCAB`), each track also carries a sparse `x` over it.
- `signal()` converts a listen to [-1, 1] from spin timing (<15s skip = -1, mid skip = -0.4, skip at >=80% ≈ neutral, full play = +0.5). `Profile.record()` applies it to features and artist, plus a short-window mood EMA.
- **Selection is LinUCB** (Li, Chu, Langford & Schapire, WWW 2010): per user, ridge regression of the reward (`record()`'s relative signal) on the feature vector; `A^-1` is kept up to date with Sherman-Morrison (d~113, persisted in the profile JSON as an upper triangle, ~45KB/user). `pickNext()` ranks by `theta.x + ALPHA*sqrt(x'A^-1 x)` (+ short-window mood fit, artist bias, artist-variety penalty), then softmax-samples the top 40 and excludes recent tracks and the last 8 artists. It replaced epsilon-greedy: exploration now targets uncertain directions. `mode` = `explore` when the pick is outside the top 10 by expected reward alone.
- `Profile.seed()` sets the **prior mean theta0** (ridge toward the onboarding picks instead of toward 0), so it fades through `A` by itself as data arrives (replaced the hand-written `1/(1+plays/30)`). Era prior = mean over the picked artists' median release year. No age is asked or guessed; era is only a feature (motivation: reminiscence bump, Holbrook & Schindler 1989, peak age disputed ~17-23).
- **Mood of the moment (owner: "I hear every genre, it depends on my mood"):** taste is non-stationary, so the long-term LinUCB is only the background. `Profile.hist` keeps the last 20 listens (track, relative signal, time); the *session* = listens since the last silence > 30 min (max 15). `sessionScore()` = `SESS_W (0.25) * sum_k SESS_GAMMA(0.85)^k * signal_k * similarity(track, listen_k)` (session kNN, Ludewig & Jannach 2018; forgetting like discounted UCB, Garivier & Moulines 2011; my adaptation, not a published algorithm). `similarity()` = cosine of the unit vectors `Track.u` (tags+moods+era, no popularity) + `SESS_ARTIST (0.5)` for the same artist. A finish pulls similar tracks up, a spin pushes them down, so the radio stays on a mood that worked. **Stay:** an artist whose latest play was finished (signal > 0.2, < 3 plays in the last 8) is exempt from the 8-play artist block. **Probe:** with < 3 plays in the session or a negative streak >= 3, the rank gets `- DIV_W (0.5) * max similarity to the last 4 served tracks` (MMR-style, Carbonell & Goldstein 1998) so picks cover different styles. All switchable through `cfg` in radio.ts (env `LT_W`, `SESS_W`, `SESS_GAMMA`, `SESS_ARTIST`, `STAY`, `PROBE`, `DIV_W`). `pickNext(catalog, profile, rng, now)` and `record(..., now)` take a clock so sims can simulate sessions.
- **Mood anchor (owner: "1-3 good songs, then random; spinning makes it worse for 7-9 spins"):** causes found in `pickNext()`: the session term decayed per listen (so a run of spins erased the finishes), a spin streak >= 3 switched PROBE on (forced diversity = more random), and the UCB bonus stayed at full size. Fix: `Profile.anchor()` = last 3 FINISHED songs of the session (decay 0.8 per finished song, only 0.97 per listen since), `anchorScore()` adds `ANCHOR_W (1)` x weighted mean similarity; while the anchor is fresh (strength > 0.5) probe is off and ALPHA is scaled toward `ANCHOR_ALPHA (0.3)`. Env: `ANCHOR_W`, `ANCHOR_GAMMA`, `ANCHOR_FADE`, `ANCHOR_ALPHA`. `sim:moody` normal listener: 71% -> 78% overall, first 8 after a switch 61% -> 69%; heavy spinner: no change (16%, finishes too rare). Untested on real logs.
- `bun run sim:moody [seeds] [plays]`: listener whose hidden taste switches every 20-40 plays (half the switches with a 40 min silence); compares variants (old / +session / +stay / +probe / all) and reports completion in the first 8 plays after a switch. Circular like the rest of the sim: it shows the mechanism works, not that real moods behave so.
- `bun run replay [minEvents]` re-runs each real user's `events` through the engine and reports AUC (finished vs spun) of the track that was actually served, with a bootstrap 90% interval, for: long-term only / session only / blend / two reference heuristics. Biased (only tracks the old engine served) and tiny; read the intervals.
- **Repeat fatigue (owner: "I like it but skipped it because it played a few hours ago"):** real log showed 10 of 160 plays were repeats of a track already served 0.3-1.7 h before (the engine only avoided the last 30 plays, i.e. minutes for a fast spinner): all 10 were spun within seconds, 6 of them songs the owner had finished before. Fix: `cfg.cooldownMs` (24 h, env `COOLDOWN_H`): `pickNext` never serves a track played inside it (falls back if the pool < 50), and `record()` learns NOTHING from a spun repeat inside the cooldown (it means "heard it already"; a finished repeat still counts, a spin after the cooldown is a normal signal). `Profile.played` is not saved in the profile JSON: `server.ts` rebuilds it from the last 7 days of `events` via `hydratePlayed()`. Sim check: 800 fast plays gave 426 repeats without cooldown, 0 with. `replay` no longer scores repeats inside the cooldown (they inflated false positives). Not handled: artist-level fatigue (the same artist many times in a day).
- **Evidence status of the mood/session work (be honest when reporting it):** in `sim:moody` with a normal listener, completion 58% (long-term only) -> 74-78% (session+stay+probe; SESS_W 0.25-0.75), probe alone adds little. With a heavy spinner (finish cap 30%, 85% early spins) there is NO gain (16% -> 17%, random 13%): finishes are too rare to carry a mood signal, also with negatives down-weighted (`SESS_NEG`). On the owner's real log, `replay` gives AUC ~0.70 (90% interval ~0.62-0.78, 137 plays, 33 finished) for the long-term model alone, session-only and the blend alike: the session term adds nothing measurable there. It is left ON by default because it is not harmful in either test; revisit when more real events exist. The simulator's hidden tastes use the same artist-level features as the engine, so its gains say nothing about song-level quality.
- **Known limit:** every feature is artist-level (Last.fm artist tags) plus era and popularity, so two songs of the same artist look the same to the engine. No free, light song-level source found yet (see 5c). Options not taken: one-time offline audio embeddings from Deezer 30 s previews (against the "no audio analysis" constraint, needs the owner's OK) or a collaborative signal from other users' `events` (needs users).
- **What has no theoretical backing (tuned in the sim only):** the reward mapping in `signal()`/`record()` (-1/-0.4/0.1/0.5, baseline subtraction, x1.5), `LAMBDA` (4) and `ALPHA` (0.5) (env overrides; sim results moved only +-2-4 points for ALPHA 0.2-1.0 and LAMBDA 2-8), `ERA_W`, the mood-EMA term, artist bias, softmax temperature 0.25, variety penalty. `LinUCB` guarantees assume a linear reward model; the real reward is not linear and `signal()` is a heuristic, so treat the guarantees as inspiration, not proof. Old profiles (saved before this engine, or with a different vocabulary/LAMBDA) restart from their onboarding prior.
- `bun run sim [plays] [seed]` (`NO_ONBOARDING=1` for pure cold start) simulates hidden-taste listeners vs a random baseline. Last run (LinUCB, normal listener): random 17-58% vs radio 85-94%, the old epsilon-greedy engine got 87-97%, so parity. Optimistic: the simulated taste uses the same features the engine sees. `NO_ERA=1` / `NO_FAM=1` remove era / familiarity from the model's vocabulary (ablation); `LAMBDA`/`ALPHA` env override the hyperparameters. Three extra tastes (`pop, 2000s nostalgia`, `pop, 2020s`, `indo pop, hits only`) differ only by era / familiarity; era ones need `bun run years` first. Their hidden taste uses the same features as the engine (circular): they show the model can learn it, not that real listeners behave so.
- `bun run trace [tasteIdx] [plays] [seed]` prints a readable simulated play log; `bun run export [plays] [seed]` writes raw CSVs to `out/` (scenarios `normal` and `sering_next`). Listener behavior knobs: env `MAX_FINISH` (cap on finish probability) and `EARLY_SPIN` (share of skips under 15s).
- Signals are **relative to the user's own habit** (owner-approved): `record()` converts the listen to an outcome in [0,1], subtracts a per-user running baseline (`Profile.baseline`) and scales by 1.5, so a habitual spinner's spins are small negatives and rare finishes are strong positives. Exploration only rises when the spin streak exceeds what the user's own `spinRate` explains.
- Artist variety is "medium" (owner asked for my recommendation): no artist repeat within 8 plays, -0.15 score per recent play of the same artist. Easy to retune in `pickNext()`.
- `sering_next` simulation (finish chance capped at 30%, ceiling ~25-30%): the old epsilon-greedy engine averaged ~9% over 3 tastes x 3 seeds (2-24%), LinUCB averages ~20% (15-23%). Baselines are in `out/baseline-old.txt`. The owner is testing with the real app first and deferred simulator realism.

## API (src/server.ts, `bun run serve`, PORT/HOST env, default 127.0.0.1:3000)

Playback is the client's job. Onboarding = the user picks 5 songs: `GET /onboarding` (`picks` = 5, `songs` = suggested famous songs of the top artists; legacy `genres`/`artists` still returned), `GET /onboarding/search?q=` (title/artist search over the playable catalog, exists ONLY for this step; the player has no search), `POST /users {trackIds}` -> `{userId}` (`genres`/`artistIds` still accepted). Each picked song seeds `Profile.seed()` through its artist's tags + median era (song-level features do not exist, see Known limit), so two songs of one artist count that artist twice, `GET /users/:id/next` -> track (`trackId` is the Deezer track id, plus `mode` explore/exploit; echo `mode` back in the event), `POST /users/:id/events {trackId, action: "spin"|"complete", listenedMs, mode}`, `GET /users/:id/debug` (learned likes/dislikes, spinRate, baseline). `GET /tracks/:id/audio` resolves a track to a playable stream via `src/youtube.ts` (search via youtubei.js; stream URL via the real yt-dlp installed in the project venv `.venv`, override with env `YTDLP`; setup: `python -m venv .venv` then `.venv/Scripts/python -m pip install yt-dlp`, keep it updated with `pip install -U yt-dlp`). Do not use youtubei.js for stream URLs: its IOS client URLs stop after ~1 MB (~64 s) because YouTube requires a PO token, and generating PO tokens / evading bot checks is off limits. `/tracks/:id/stream` is a same-origin range proxy (googlevideo returns 403 without CORS headers to browser requests, so bounded ranges are translated). Matching: search "artist title", reject live/cover/remix/karaoke etc., require the song title in the video title and duration within 12s of Deezer's, prefer "Official Audio"/Topic uploads; results cached in `yt_matches` (negative results too, and those tracks are never served again). Stream URLs are cached in memory until shortly before `expire`. This violates YouTube's ToS: personal testing only. `GET /` serves `src/ui.html`: onboarding chips, then a player with only a SPIN button (no like, no search); it prefetches and buffers the next track 12s into the current one so a spin or song end is instant. Known limitation: the prefetched pick is made before the current track's event is recorded, so one pick of lag. No auth yet (local prototype). Profiles are JSON in `users`; every event is appended to `events` (user_id pseudonymous, signal, hour, dow) as the training data for a future cross-user recommender.
- Not built yet: persistence of profiles/events, time-of-day context, track-level tags, any UI/API.

## Product intent (from the owner, not yet implemented)

A music app that behaves like a **personalized radio**:

- No search, no browsing artists/songs. The user only gets a continuous, effectively random stream.
- Personalization is the core: a custom algorithm infers which songs the user likes and what mood they are in.
- Onboarding seeds the model: the user picks a few categories (genres) and artists as the initial taste profile (cold start).

- Playback control is a **spin button** (next track). Spin is the main implicit feedback signal: weight it by listen time (early skip = strong negative, skip near the end ≈ neutral, full play = positive), apply it to track attributes (genre/artist/tempo/energy) rather than the single track, and treat rapid consecutive spins as a mood-mismatch signal. There is deliberately **no like button** (it would break the "magic" feel): all taste inference must come from implicit signals (listen time, spin timing, replays, time of day), never from explicit rating UI.

Data scope: the music library is for **research data only** (metadata, tags, audio features, listening behavior), not audio. Playback is handled by the owner separately and is out of scope. Coverage must be **commercial music, including Indonesian songs**, not indie/royalty-free catalogs (no Jamendo/FMA/NCS-style sources).

Constraints: free sources only, and the server is weak, so keep everything lightweight: no full database dumps, no audio analysis (Essentia), no heavy DB. Fetch from free APIs (Deezer, Last.fm, MusicBrainz) in small rate-limited batches into SQLite; mood/energy comes from Last.fm tags, not audio features.

Agreed design principles (implicit-only, "magic" feel):

- Positive signals: full play, surviving the first ~10-15s, never spun despite repeated plays, volume raise, returning at the same time of day.
- Reserve ~10-20% of plays for out-of-profile exploration (bandit-style); promote what survives.
- Transitions between moods are gradual (bridge tracks), never abrupt; a spin must be followed by a noticeably better pick.
- Context-aware by time of day / weekday vs weekend, with no user configuration.
- Never explain recommendations in the UI ("because you liked X").
- Cold start: onboarding picks dominate the profile in week one, then behavior gradually takes over. Mood uses a short window (last ~5-10 tracks); long-term taste uses full history.

Design implications to keep in mind: there should be no catalog-lookup UI or API surface for users; the recommender/"next track" selection is the central module; user feedback signals (skip, completion, like) should feed back into the taste/mood model.

## Learned ranking, logging and the song-level experiments (added)

- **Logging for evaluation:** `serves` table (db.ts) stores, for every served track, its exact selection probability (`propensity`) and the ranking components (`comps` JSON, see `components()` in radio.ts). Use it for off-policy evaluation (IPS / doubly robust) once there is data. `pickNext()` returns `{track, mode, prop, comps}`.
- **`bun run fit`** (src/fit.ts): replays every user's `events` and fits L2 logistic regression of "finished" on the ranking components (leave-one-user-out CV picks the ridge, ablation table, standard errors). `--write` writes `data/weights.json`, which switches the engine to `pickLearned()` (rank = log-odds, odds-proportional sampling); delete the file to go back. NOT written so far: on 475 plays / 9 users the learned model did not beat the hand-tuned score (within-user AUC 0.68-0.70 vs 0.71). What did help: `ancMax` (max similarity to a song finished this session) and the long-term mean; the anchor MEAN, uncertainty (`sd`) and diversity had no demonstrable weight. Rerun when there are several hundred new events.
- **`data/vocab.json` pins the LinUCB vocabulary.** The top-100 tags shift whenever `daily` adds artists, and a profile saved under another vocabulary silently restarts from its onboarding prior (this would have reset every user on a server restart). Delete the file only to deliberately rebuild it (resets all learned profiles).
- **Neighbourhood + stay fix (cfg.hood, env HOOD, default 60):** while a finished song exists in the session only its 60 nearest neighbours (by max similarity) are candidates and the UCB bonus is 0; "stay" now uses the artist's BEST play in the last 8 (a single spin no longer blocks an artist whose song was just finished). Not proven: sim:moody is too noisy (+-5 points between near-identical variants) and circular. `HOOD=0` restores the old behaviour. Owner's complaint it targets: after a finished song the next one is off, spinning drifts further away.
- **Song-level similarity experiments (all on ~200 tracks real users played, within-user leave-one-out AUC of "mean similarity to the user's other finished songs", 2-3 users, so read as a first look):** tag similarity 0.82-0.84 (no same-artist bonus). Audio embeddings (CLAP via transformers.js in Bun, `bun run embed:test`, ~1.1-1.6 s/track, whole catalog ~7-9 h): centered audio alone 0.70-0.76 same-artist-allowed and 0.43-0.63 across artists (`clap-htsat-unfused` worse than `larger_clap_music_and_speech`); tag+audio +0.05 only when same-artist songs count, no gain across artists. Language from lyrics (LRCLIB, `bun run lyrics:test`, 92% coverage; only language is stored, lyrics are discarded): AUC 0.46, tag+language slightly worse. Conclusion so far: neither audio nor lyric language is worth the cost; not run on the whole catalog. `track_emb` (PK track_id+model) and `track_lyrics` tables exist but nothing in the engine reads them. Untested ideas: public Deezer playlist co-occurrence (item2vec), lyric theme vectors, Last.fm `track.getSimilar` (42% coverage, near 0 for Indonesian tracks).

## Online radio direction (added)

Project is shifting from per-user radio to an AI-hosted online radio: shows (e.g. "GAS TERUS!", host Vivan, 07:30-08:30) with pre-recorded ElevenLabs voice segments in `scripts/<date>/<start>-<end>.md` (`# VOICE n` blocks, v3 audio tags) + `VOICE-n.mp3`, songs chosen by the Krungu engine. No rundown format, scheduler or playout yet.
- `src/playlist.ts` (`bun run playlist "Artist1,Artist2" "genre" N`): `buildPlaylist(spec)` = the engine as one listener whose taste is the segment spec (seed artists / genre tags, `minFam`); picks are recorded as finished so the anchor keeps the set coherent, `cfg.stay` is off so the same artist is not played back to back. Seeding with a broad tag like `indonesian` drifts to odd picks; artist seeds work better.
- `src/mixer.ts` is the reusable mixing module: `renderSequence(clips, out)` joins voice/song clips, each transition chosen by its neighbours (voice->song talk-over: song starts OVERLAP 6 s before the voice ends, ducked to 0.3 then ramps up; song->song crossfade XFADE 4 s; song->voice: outro drops to bed 0.25 for BED 6 s, voice enters, song fades out 3 s; voice->voice 0.4 s gap), loudness-normalized (voice -16, song -18 LUFS) + limiter; returns the timeline. `resolveSongs(tracks, n, dir)` = YouTube match + cached yt-dlp download. Songs are trimmed to where the music really is (`musicBounds()`: ffmpeg silencedetect at -42 dB, env SILENCE_DB): YouTube audio has ~1 s of silence at the start and 2.6-7.2 s at the end (measured on 5 files), and mixing by file length put crossfades/beds inside that silence (owner: 'song went empty, the next song came in late'). All other parameters are the SAME fixed defaults for every song (env tunables); nothing else is song-aware yet (no vocal-start / outro-shape detection; a long fade-out tail above -42 dB still counts as music). Owner listened to the result and liked the song-to-song mix. `bun run chain [voiceA] [voiceB] [artists] [songs]` (src/chain.ts) renders VOICE a -> songs -> VOICE b into `out/mix/chain.mp3`.
- `src/mix.ts` (`bun run mix [voice.mp3] [artists]`): ffmpeg (installed via winget, found on PATH or WinGet Links) transition experiment, writes `out/mix/`: voice->song fade, voice->song talk-over (song ducked under the voice tail, then ramps up), song->voice (outro drops to a bed, voice enters). Loudness-normalized (voice -16, song -18 LUFS), params via env (OVERLAP, DUCK, RAMP, BED, BEDG, EXCERPT, TAIL). Song audio via yt-dlp (personal testing only). Judged by ear; entry points are manual (no intro/vocal-start detection yet).
- Segment types in the mixer (`Clip.kind`): `voice` (optional `bed` = looped music bed under it, BED_GAIN 0.18 after normalizing, starts 1.5 s early, 1.5 s tail; skipped when a song's outro already plays under the voice), `song`, `bumper` (jingle/ID/intro/outro, takes time), `stinger` (short effect laid over the cut into the NEXT clip, takes no time). Transition table is `overlapOf()` in mixer.ts (e.g. bumper->voice: announcer talks up over the last 2 s, jingle ducked; song->bumper 1.5 s; bumper->song 1 s).
- `src/rundown.ts` (`bun run rundown scripts/<date>/<slot>.rundown.txt`): one text line per item (`bumper intro-gas-terus`, `voice VOICE-1 bed=morning-1`, `song 2`, `stinger whoosh-1`; headers `artists:`/`genres:`/`minFam:`). One engine playlist per slot, handed out in order. Output `out/rundown/<slot>.mp3` + printed as-run timeline. Placeholder assets in `assets/{beds,bumpers,stingers}` come from YouTube (see assets/README.md), to be replaced by licensed ones. First full render (18:34, 4 songs): the bed removes all 24 silent speech gaps of VOICE-1 (silencedetect -42 dB: 24 -> 0). Voice option `up=N`: the bed plays alone N s at full level (the intro), ducks under the voice and keeps going until the next song has come in (fades 3 s under it), instead of a separate intro bumper followed by a different bed. The bed file is looped (stream_loop), a loop seam is audible when the show is longer than the file.
- Segment playlist (`src/playlist.ts`): default mode `taste` = fixed taste: candidates scored by `similarity()` to the 3 best-known songs of each seed artist (mean of the 2 closest seeds) + 0.3*fam, sampled (temp 0.08) from the best 40, no artist twice within 6 picks. Mode `drift` (the old session-engine walk, every pick recorded as finished) wandered: pop-indie seeds ended in gospel/campursari. Taste mode is still artist-level tags only, so it can slip (religious / dangdut artists sharing tags). Judged by eye on 2 seeds, not measured.
- Pinned playlists (optional; the current rundown does NOT use one, the owner wants Krungu to choose songs per render and the voices never name them): scripts that name songs need a fixed song list. `bun run playlist:pin <out.json> "Artists" <n> [seed] ["Excluded,Artists"]` (src/pin-playlist.ts) picks with taste mode + `announce: true` (`announceable()`: title <= 6 words, plain Latin letters; `cleanTitle()` strips "(feat/Live)" and "- Remastered"), keeps only songs with a YouTube match, writes JSON. A rundown header `playlist: file.json` makes `song n` use exactly those songs in order (errors if one cannot be resolved).
